# MEMBRA Federation Map

This document consolidates the accessible MEMBRA repositories into one operating architecture. The goal is not to collapse every repository into one codebase immediately. The goal is to make every repo act as a coordinated product surface with shared contracts, shared events, and clear ownership.

## Umbrella repository

### `overandor/membra`

Role: federation/meta repository and primary architecture anchor.

Responsibilities:

- system architecture
- shared contracts
- cross-repo development plan
- deployment topology
- investor/customer narrative
- integration standards
- common event vocabulary
- canonical product roadmap

## Product and intelligence core

### `overandor/Membra_kpi`

Role: image-to-SKU marketplace operating system.

Responsibilities:

- iPhone/photo ingestion
- image quality scoring
- duplicate detection
- SKU identification
- proprietary listing packets
- MEMBRA LLM DAG
- ProofBook events
- private listing drafts
- owner-confirmed marketplace publication
- payout eligibility records

This repo is the current highest-value product nucleus.

## API boundary

### `overandor/Membra_api`

Role: public/internal API gateway.

Responsibilities:

- versioned API facade
- auth gateway
- request validation
- service routing
- API documentation
- integration keys
- webhook ingestion

Target relationship: should call `Membra_kpi` for image/listing conversion and expose stable `/api/v1` endpoints.

## Admin/operator surface

### `overandor/Membra_admin-`

Role: operator review console.

Responsibilities:

- operator queues
- proof review
- publication gating
- risk escalation
- owner-field requests
- admin decisions
- compliance notes

Target relationship: should consume proprietary listing packets and DAG runs from `Membra_kpi`.

## Proof and audit subsystem

### `overandor/Membra_proofbook`

Role: standalone audit/proof service.

Responsibilities:

- hash ledger
- proof manifests
- event-chain verification
- QR/NFC proof artifacts
- exportable diligence packets

Target relationship: should standardize ProofBook records generated by `Membra_kpi`, `membra-qr-gateway`, and admin review.

## QR gateway

### `overandor/membra-qr-gateway`

Role: QR/NFC artifact routing and scan telemetry.

Responsibilities:

- QR artifact generation
- scan recording
- destination routing
- campaign analytics
- proof-of-scan events

Target relationship: should emit `qr.scan.recorded` and `artifact.created` events into ProofBook.

## Wallet and eligibility

### `overandor/Membra_wallet`

Role: payout eligibility and non-custodial ledger surface.

Responsibilities:

- payout eligibility records
- wallet events
- non-custodial settlement state
- Stripe/external rail references
- owner earnings dashboard

Boundary: MEMBRA should record eligibility and external settlement references only. It should not custody funds.

## Contracts

### `overandor/Membra_contracts`

Role: smart-contract or on-chain interface sandbox.

Responsibilities:

- contract interfaces
- proof anchors
- optional non-custodial settlement references
- simulation/dry-run-only development until security reviewed

Boundary: no private keys, no unsafe transaction automation, no production fund custody without formal audit.

## Canonical product loop

```text
mobile/photo upload
→ Membra_kpi image quality + duplicate analysis
→ Membra_kpi SKU identification
→ Membra_kpi proprietary listing packet
→ Membra_kpi LLM DAG
→ Membra_proofbook event hashes
→ Membra_admin operator review
→ Membra_api stable external access
→ Membra_wallet payout eligibility
→ membra-qr-gateway QR/NFC scan telemetry
→ vertical repos specialize campaign/storage/wear/relay logic
```

## Cross-repo rule

Every repo should implement or document these contracts:

- `membra.event.schema.json`
- `membra.listing_packet.schema.json`
- `membra.proofbook.schema.json`
- `membra.service_manifest.json`

No repo should invent a separate lifecycle for owners, listings, proof, or payout eligibility.
