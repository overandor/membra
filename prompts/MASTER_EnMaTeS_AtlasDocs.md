SECTION 3 — NON-NEGOTIABLE BUILD PRINCIPLES
====================================================================

Follow these rules strictly:

1. Real implementation only.
Do not produce placeholder-only architecture. Scaffolds are allowed only when they are functional and clearly extensible.

2. No fake completion.
Do not say something is complete unless code exists and verification has passed.

3. Keep the repo deployable.
After each meaningful increment, the app should remain installable, buildable, and understandable.

4. Stabilize before expanding.
If tests, typecheck, lint, or build fail, switch to repair mode before adding features.

5. Prefer small reversible increments.
Large changes must be decomposed into safe PR-sized units.

6. Database-backed where required.
Docs pages, API categories, API endpoints, audit logs, API keys, and search index must have database models.

7. Typed end-to-end.
Use TypeScript types, Prisma types, Zod validation, and typed response helpers.

8. Consistent API contracts.
All API endpoints must return the same structured response format.

9. Security first.
Do not hardcode secrets. Do not expose admin writes publicly. Do not store API keys in plaintext.

10. Operational readiness matters.
Health checks, readiness checks, logs, request IDs, deployment instructions, and monitoring instructions are part of the product, not optional extras.

11. Documentation is part of the deliverable.
The README must explain setup, development, deployment, database, auth, OpenAPI export, search, and extension paths.

12. Never skip file paths.
When generating files, include the full file path before each file.

13. Never omit critical files.
Do not say "same as above," "implementation omitted," "add remaining files similarly," or "left as an exercise."

14. Self-repair continuously.
After errors, inspect, patch, rerun, and continue.

15. Capacity-adjust to requestivity.
Adapt task size, context depth, repair mode, milestone granularity, and verification depth based on the live state of the project.

====================================================================

Requestivity is the combined pressure and direction generated by:

- user intent
- product goal
- current repo state
- current branch state
- test status

- deployment status
- available context

- current blockers
- error load
- infrastructure state
- security risk
- product value
- complexity level
- stability level
- implementation uncertainty

You must continuously measure requestivity and adjust capacity.

Capacity adjustment means:

- increase decomposition when scope is large
- reduce decomposition when task is small
- switch to repair mode when verification fails
- switch to stabilization mode when the repo is unstable
- switch to documentation mode when features exist but usage is unclear
- switch to observability mode when the app works but lacks operations readiness
- switch to security mode when sensitive operations exist
- switch to deployment mode when local functionality is complete
- switch to product polish mode when the core is stable
- summarize context when memory pressure grows
- preserve working state before adding risky features
- avoid global rewrites unless necessary

The agent must not blindly continue generating files if the current state is unknown.

Default loop:

PROFIT-ASSESS → PLAN → INSPECT → PATCH → VERIFY → REPAIR → COMMIT → REPORT → CONTINUE

SECTION 9 — API RESPONSE CONTRACT
====================================================================

All JSON APIs must return one of these shapes.

Success:

{
  "success": true,
  "data": {},
  "meta": {},
  "error": null
}

List success:

{
  "success": true,
  "data": [],
  "meta": {
    "page": 1,
    "limit": 20,
    "total": 100,
    "hasMore": true
  },
  "error": null
}

Failure:

{
  "success": false,
  "data": null,
  "meta": {},
  "error": {
    "code": "ERROR_CODE",
    "message": "Human-readable message",
    "details": {}
  }
}

Required standard error codes:

VALIDATION_ERROR
UNAUTHORIZED
FORBIDDEN
NOT_FOUND
CONFLICT
RATE_LIMITED
DATABASE_ERROR
INTERNAL_ERROR
METHOD_NOT_ALLOWED
BAD_REQUEST
SERVICE_UNAVAILABLE

Implement shared helpers:

ok(data, meta?)
paginated(data, pagination)
fail(code, message, status, details?)
handleApiError(error)
